Fully Homomorphic Encryption: A Beginner-to-Systems Guide

This page is written for the case where you know essentially nothing about fully homomorphic encryption. The goal is to build the subject from the ground up: what encryption is, why computation on encrypted data is hard, how FHE solves that problem, why noise and bootstrapping appear, how matrix arithmetic fits modern machine learning, and why compiler systems such as HEIR matter for making the whole stack usable.

The emphasis is on conceptual structure. Each section introduces the object, explains why it matters, gives the cleanest mental model available, and highlights the vocabulary you need in order to read papers and watch talks without getting lost.

Part I: Why We Need FHE

1.1 The Basic Problem

Suppose you have sensitive data: medical records, financial transactions, private prompts, model inputs, or enterprise documents. You want some untrusted server to compute on that data for you. Traditional encryption protects the data at rest and in transit, but not during computation. The usual workflow is:

  • Encrypt data locally.
  • Send ciphertext to the server.
  • Server must decrypt to compute.
  • So the server learns the plaintext.
Goal. We want an encryption scheme that allows useful computation directly on ciphertexts, so that the server never sees the underlying plaintext.
FHE is about removing the tension between privacy and usefulness. Ordinary encryption gives privacy but blocks computation. Plain outsourced computation gives usefulness but loses privacy. FHE tries to get both at once.

1.2 The Dream Output Condition

If the plaintext is \(m\), and \(f\) is some function we want to compute, we would like the server to transform an encryption of \(m\) into an encryption of \(f(m)\), without ever learning \(m\) or \(f(m)\).

Correctness pattern. If \(c = \mathrm{Enc}(m)\), the server computes \[ c' = \mathrm{Eval}(f, c), \] and then the client decrypts: \[ \mathrm{Dec}(c') = f(m). \]
Example. A hospital could encrypt patient features, a cloud service could run a risk-scoring model on the encrypted inputs, and only the hospital would learn the final risk score after decryption.

Part II: Basic Cryptography Background

2.1 Plaintext, Ciphertext, Keys

Plaintext. The original readable data.
Ciphertext. The encrypted form of the data.
Secret key. The private object used to decrypt.
Public key. The public object others can use to encrypt to you.

In public-key encryption, anyone can encrypt to the owner of the secret key, but only the secret-key holder can decrypt.

2.2 Symmetric vs Public-Key Encryption

Symmetric-key encryption. The same shared secret key is used for encryption and decryption.
Public-key encryption. Encryption uses a public key and decryption uses a secret key.
FHE is usually discussed in the public-key setting because outsourcing computation naturally fits the model where many parties encrypt data to one party that owns the decryption key.

2.3 What Security Usually Means

Encryption should hide the plaintext from anyone who does not have the secret key. In modern cryptography, security is expressed as the inability of efficient adversaries to distinguish encryptions of chosen messages.

Important mindset. In cryptography, "secure" does not mean "looks random to me." It means the scheme resists mathematically formal attack models under explicit hardness assumptions.

Part III: The Core Idea of Homomorphic Encryption

3.1 What "Homomorphic" Means

Homomorphism. A structure-preserving map. In this context, operations on ciphertexts correspond to operations on plaintexts.

A toy additive example would satisfy: \[ \mathrm{Dec}(c_1 \oplus c_2) = m_1 + m_2, \] whenever \(c_1 = \mathrm{Enc}(m_1)\) and \(c_2 = \mathrm{Enc}(m_2)\).

3.2 Partial, Somewhat, Leveled, and Fully Homomorphic Encryption

Partially homomorphic encryption. Supports only a restricted class of operations, such as just addition or just multiplication.
Somewhat homomorphic encryption. Supports both addition and multiplication, but only for a limited computation size before decryption fails.
Leveled FHE. Supports all circuits up to a chosen depth bound.
Fully homomorphic encryption. Supports arbitrary bounded computation in principle, because the scheme can refresh ciphertexts as needed.
Key structural difference. The jump from "leveled" to "fully" is bootstrapping. A leveled scheme can only survive a predetermined amount of multiplicative work. A fully homomorphic scheme can repeatedly refresh the ciphertext and continue.

Part IV: Noise, Depth, and Bootstrapping

4.1 Why Noise Appears

Modern lattice-based encryption schemes deliberately add randomness and error terms. This noise is not a bug; it is central to security. But as homomorphic operations are applied, the noise grows.

Noise. A hidden error component inside a ciphertext that must stay within a certain range for decryption to remain correct.
Think of each ciphertext as carrying a "budget." Additions spend a little of it. Multiplications spend much more. When the budget is exhausted, the ciphertext still exists, but it no longer decrypts reliably.

4.2 Multiplicative Depth

Multiplicative depth. The maximum number of multiplications on any path through the arithmetic circuit being evaluated.
Example. The expression \((ab)(cd)\) has multiplicative depth \(2\): first compute \(ab\) and \(cd\), then multiply the results.
Why depth matters more than count. Many FHE costs and parameter choices are driven not by the total number of operations but by how many multiplicative layers are stacked before a refresh.

4.3 Bootstrapping

Bootstrapping. A refresh procedure that reduces the effective noise of a ciphertext so that more homomorphic computation can continue.

Historically, bootstrapping was the key conceptual breakthrough that made fully homomorphic encryption possible.

The slogan is: use encrypted computation to clean up an encrypted ciphertext. It sounds circular at first, but that circularity is exactly the genius of the idea.
Practical consequence. When people say FHE is slow, a large part of that complaint is really about the cost of high-depth operations and bootstrapping.

Part V: Algebra and Linear Algebra Prerequisites

5.1 Why Cryptography Uses Strange Algebra

If you already know matrix multiplication, the biggest shift in cryptography is that we stop working over the ordinary real numbers and start working in more rigid algebraic worlds. These worlds are chosen because they make three things possible at once:

  • Arithmetic can be done efficiently by computers.
  • The structure is rich enough to encode useful computation.
  • Recovering hidden information appears computationally hard.
In linear algebra, the algebraic setting is usually chosen because it models geometry or data. In cryptography, the algebraic setting is often chosen because it creates a controlled mixture of useful structure and computational hardness.

5.2 Modular Arithmetic

FHE schemes are built over arithmetic modulo one or more integers \(q\). To compute modulo \(q\) means we only care about remainders after division by \(q\). Two numbers are treated as equivalent if they differ by a multiple of \(q\).

Congruence modulo \(q\). We write \[ a \equiv b \pmod q \] if \(q\) divides \(a-b\).
Example. Modulo \(7\), one has \(5+4 \equiv 2 \pmod 7\), since \(9\) leaves remainder \(2\) on division by \(7\).
Another example. Modulo \(7\), one has \(6\cdot 6 = 36 \equiv 1 \pmod 7\).
The phrase "wrap around" is accurate. On a clock, \(11+3=2\) if the clock has 12 hours. Modular arithmetic is that same idea, except the modulus \(q\) can be very large and chosen for algorithmic reasons.

5.3 Fields vs Rings

Many students first meet modular arithmetic in settings where everything behaves nicely, especially when the modulus is prime. Cryptography often works in settings that are slightly less nice but much more useful.

Field. A number system where you can add, subtract, multiply, and divide by every nonzero element.
Ring. A set with addition and multiplication, where addition behaves like an abelian group and multiplication distributes over addition, but division by nonzero elements is not generally available.
Field example. \(\mathbb{Z}_7\) is a field because \(7\) is prime, so every nonzero residue has a multiplicative inverse.
Ring example. \(\mathbb{Z}_{8}\) is a ring but not a field. For example, \(2\) has no inverse modulo \(8\).
A ring is "less flexible" than a field, but that extra rigidity is not a problem for cryptography. In fact, many useful cryptographic objects naturally live in rings.

5.4 What \(\mathbb{Z}_q\) Actually Means

The notation \(\mathbb{Z}_q\) means the integers modulo \(q\). Its elements are residue classes, which you can picture concretely as the set \[ \{0,1,2,\dots,q-1\}. \] Arithmetic is done as usual and then reduced modulo \(q\).

Why this matters. When a paper says that a vector has entries in \(\mathbb{Z}_q\), it means each coordinate is only tracked modulo \(q\). So addition and multiplication happen coordinatewise with reduction modulo \(q\).

5.5 Polynomials as Algebraic Containers

A polynomial is an expression like \[ a_0 + a_1X + a_2X^2 + \cdots + a_dX^d. \] In FHE, the coefficients \(a_i\) often live in \(\mathbb{Z}_q\), so all coefficient arithmetic is done modulo \(q\).

Example. Over \(\mathbb{Z}_5\), the polynomials \[ 4 + 3X + X^2 \qquad\text{and}\qquad 2 + 4X \] add to \[ (4+2) + (3+4)X + X^2 \equiv 1 + 2X + X^2 \pmod 5. \]
A polynomial ring lets you package many numbers into one algebraic object. That is one reason it is so natural for batched encrypted computation.

5.6 Quotient Rings and Why \(X^N+1\) Appears

In RLWE-based cryptography, one often works in polynomial rings such as \[ R_q = \mathbb{Z}_q[X]/(X^N+1). \] This notation can look intimidating, but the idea is manageable if you read it in two pieces:

  • \(\mathbb{Z}_q[X]\) means polynomials whose coefficients are in \(\mathbb{Z}_q\).
  • Dividing by \((X^N+1)\) means we identify polynomials that differ by a multiple of \(X^N+1\).
Quotient-ring rule. In \(R_q = \mathbb{Z}_q[X]/(X^N+1)\), we are allowed to replace \(X^N\) by \(-1\).
Example. If \(N=4\), then in this ring, \[ X^4 \equiv -1, \qquad X^5 \equiv -X, \qquad X^6 \equiv -X^2. \] So every polynomial can be reduced to degree at most \(3\).
This means the ring behaves like a fixed-size vector space of dimension \(N\), because every element can be represented by its \(N\) coefficients on \[ 1, X, X^2, \dots, X^{N-1}. \] You can think of a ring element as an \(N\)-dimensional vector with a special multiplication rule.

5.7 Why Polynomial Multiplication Is Interesting

Addition of ring elements is just coefficientwise addition, so it looks like vector addition. Multiplication is more interesting: multiplying polynomials mixes the coefficients together in a structured way.

Example. If \[ a(X)=a_0+a_1X \qquad\text{and}\qquad b(X)=b_0+b_1X, \] then \[ a(X)b(X)=a_0b_0 + (a_0b_1+a_1b_0)X + a_1b_1X^2. \] The coefficients are being convolved together.
This is one reason rings are so useful for cryptography: multiplication is richer than plain coordinatewise multiplication, but still structured enough to implement efficiently.

5.8 Vectors, Matrices, and Ring Elements

Since the referenced material revolves around encrypted matrix arithmetic, you should know:

  • Vector addition and scalar multiplication.
  • Dot products.
  • Matrix addition.
  • Matrix multiplication.
  • Hadamard (entrywise) multiplication.
  • Transpose and conjugate transpose.
Matrix multiplication formula. If \(A \in \mathbb{R}^{m \times n}\) and \(B \in \mathbb{R}^{n \times p}\), then \[ (AB)_{ij} = \sum_{k=1}^{n} A_{ik}B_{kj}. \]
The bridge to cryptography is that a ciphertext is often not "just a number." It is closer to a structured algebraic object, sometimes best viewed as a small tuple of ring elements. The whole game is to make arithmetic on those structured objects correspond to useful arithmetic on the underlying plaintext data.

5.9 The Minimum Lattice Intuition You Need

Most practical FHE is based on lattice problems such as LWE and RLWE. You do not need full lattice theory at the beginning, but you should know the rough picture.

Lattice. A regular grid of points in high-dimensional space generated by integer combinations of basis vectors.
Simple 2D picture. In two dimensions, the ordinary integer grid \[ \{(m,n): m,n \in \mathbb{Z}\} \] is a lattice.
In high dimensions, some lattice problems appear computationally hard. Modern lattice cryptography hides secrets inside linear-algebraic relationships disturbed by small noise.

5.10 LWE and RLWE at a High Level

LWE. Learning With Errors. Roughly: recover a hidden vector \(s\) from noisy linear equations.

A typical LWE sample looks like \[ (\mathbf{a}, b) \qquad\text{with}\qquad b \approx \langle \mathbf{a}, \mathbf{s} \rangle + e \pmod q, \] where \(\mathbf{a}\) is public, \(\mathbf{s}\) is secret, and \(e\) is a small error term.

RLWE. Ring Learning With Errors. The same basic idea as LWE, but with vectors replaced by ring elements and inner products replaced by ring multiplication.
Why the error term matters. Without noise, the equations would often be solvable by standard linear algebra. The small noise is what turns an easy algebra problem into a hard cryptographic one.
This is one of the biggest conceptual differences from ordinary math classes: in cryptography, adding a tiny error is not sloppiness. It is often the source of security.

5.11 Why Ring-LWE Is Attractive for FHE

  • Ring elements can represent many coefficients at once.
  • Polynomial/ring multiplication can be implemented very efficiently.
  • The resulting ciphertexts support rich structured arithmetic.
  • The hardness assumptions are compatible with modern post-quantum cryptography.
Takeaway. RLWE is popular not because mathematicians like complicated notation, but because it gives an unusually strong combination of efficiency, algebraic structure, and believed security.

5.12 What You Actually Need to Remember

For now, the essentials are: arithmetic is done modulo \(q\); ciphertext components often live in polynomial quotient rings; those ring elements behave like fixed-length coefficient vectors with a special multiplication rule; and the security comes from noisy high-dimensional algebraic problems such as LWE and RLWE.

Part VI: Major FHE Scheme Families

6.1 BFV and BGV

BFV and BGV are classic lattice-based schemes designed for exact arithmetic over integers modulo some value. They are useful when exact combinatorial or modular computation matters.

If your problem really is discrete arithmetic, these schemes feel natural. If your problem looks like floating point machine learning, they are often less natural than CKKS.

6.2 CKKS

CKKS. An approximate homomorphic encryption scheme designed for efficient arithmetic on vectors of approximate real or complex values.

CKKS is widely used in private inference because neural-network workloads naturally tolerate approximation.

Why CKKS is popular in ML. Neural networks already operate with floating-point approximations, quantization, and numerical tolerance. An approximate encryption scheme fits that culture much better than a strictly exact one.

6.3 TFHE-Style Schemes

TFHE-family schemes are often optimized for Boolean or small-integer operations and for very fast bootstrapping at the level of bits, gates, or lookup-table style operations.

CKKS is often the “linear algebra” scheme. TFHE is often the “logic / programmable bootstrapping / LUT” scheme. That is an oversimplification, but it is a useful first approximation.

6.4 Why New Matrix-Native Schemes Matter

The referenced matrix-arithmetic work is exciting because standard FHE schemes were not originally designed around matrix multiplication as the first-class primitive, even though matrix multiplication dominates modern ML.

Main systems insight. If the dominant workload is matrix arithmetic, then it can be worth redesigning the cryptographic representation so that matrix operations become native rather than awkwardly emulated.

6.5 Gentry-Lee and the GL Direction

The Gentry-Lee direction, often referred to informally as the GL scheme in recent talks and summaries, is important because it pushes this matrix-native viewpoint much more aggressively than traditional FHE pipelines.

High-level idea. Instead of treating matrix arithmetic as something that must be assembled out of vector-slot tricks, the Gentry-Lee approach aims to make matrix operations themselves much more natural inside the encrypted representation.

You should think of GL not merely as "another FHE scheme," but as part of a design shift. Traditional FHE systems often begin with a ciphertext model optimized for scalar or vector arithmetic, and then build matrix multiplication indirectly. The Gentry-Lee perspective asks whether the representation itself should be redesigned around matrix workloads from the start.

If modern private AI spends most of its time doing matrix multiplication, then a scheme built around matrix arithmetic may be a better fit than a scheme that only becomes matrix-friendly after many layout conversions and auxiliary operations.

6.6 How GL Differs from the Usual CKKS Mental Model

In the usual CKKS mental model, you pack many values into slots of a ciphertext, then spend substantial effort arranging, rotating, summing, converting, and aligning those slots so the desired linear algebra happens.

CKKS-style mindset. Start with packed vectors, then engineer matrix arithmetic by clever slot layout, rotations, rescaling, and kernel design.
GL-style mindset. Start by asking how matrices themselves should live inside ciphertexts so that matrix operations are closer to native operations of the scheme.
Conceptual contrast. CKKS is excellent and broadly useful, but its native abstraction is not "encrypted matrix" in the strongest sense. The GL direction is exciting because it tries to reduce that mismatch between the algebraic object used by the scheme and the algebraic object used by the application.

6.7 What to Learn About GL Specifically

If you want to understand Gentry-Lee properly, these are the exact questions to keep in mind:

  • What is the plaintext object: scalar, vector, matrix, or batched family of matrices?
  • What operations are supported naturally: addition, matrix multiplication, Hadamard multiplication, transpose, rotations?
  • Which standard expensive steps are reduced or removed?
  • How is ciphertext-ciphertext matrix multiplication expressed inside the scheme?
  • How does the scheme interact with hardware designed for dense matrix arithmetic?
Best beginner summary. Gentry-Lee matters because it asks whether fully homomorphic encryption can be redesigned so that matrix arithmetic is not a painful special case, but a central native feature.

Part VII: The Standard FHE Operations Vocabulary

7.1 Addition and Multiplication

Every practical FHE user needs to distinguish plaintext-ciphertext operations from ciphertext-ciphertext operations. The latter are usually much more expensive.

Cheaper pattern. Multiply an encrypted vector by a known public constant matrix.
Harder pattern. Multiply an encrypted matrix by another encrypted matrix.

7.2 Relinearization

Relinearization. A post-multiplication procedure that compresses a larger ciphertext form back into the standard ciphertext size.
Multiplication often makes ciphertexts algebraically “fatter.” Relinearization shrinks them back into the normal format, at a cost.

7.3 Key Switching and Rotation Keys

Key switching. Transforming a ciphertext under one effective key representation into a ciphertext under another, without decryption.

Many operations such as rotations require auxiliary evaluation keys. These keys improve capability but increase memory usage.

7.4 Modulus Switching and Rescaling

In exact schemes, modulus switching helps manage noise. In CKKS, rescaling additionally manages the scale attached to approximate encodings after multiplication.

Important distinction. Newcomers often mix up “noise management” and “precision management.” In CKKS, rescaling is tied to both.

Part VIII: Packing, Slots, and SIMD

8.1 Why Packing Exists

FHE would be nearly unusable if each ciphertext carried only one scalar. Modern schemes therefore pack many values into one ciphertext and apply the same operation to all of them simultaneously.

Slots. The packed components of a ciphertext that can often be manipulated in SIMD style.
SIMD. Single instruction, multiple data: one operation acts on many packed values at once.

8.2 Rotations

Packed computation is powerful only if we can move data around inside the packed layout. Rotations shift slot positions so that different values can interact.

Example. A dot product can be implemented by elementwise multiplication followed by a sequence of rotations and additions that sum the coordinates.

8.3 Layout Matters

In FHE, performance often depends less on the abstract mathematics of the computation and more on how the data is arranged in ciphertext slots. Good layout can save huge numbers of rotations and key-switches.

Part IX: Matrix Arithmetic Under Encryption

9.1 Why Matrix Multiplication Is Central

Matrix multiplication is the computational engine of much of scientific computing and machine learning. If you can do encrypted matrix multiplication efficiently, you unlock a large fraction of the useful workload.

Systems principle. Since neural networks are dominated by linear layers, attention projections, and other tensor contractions, the efficiency of encrypted matrix multiplication often determines whether private AI is viable at all.

9.2 Plaintext-Ciphertext vs Ciphertext-Ciphertext Matrix Multiplication

Plaintext-ciphertext multiplication. One matrix is public/known; the other is encrypted.
Ciphertext-ciphertext multiplication. Both matrices are encrypted.

The second problem is conceptually cleaner from a privacy perspective, but also much harder and more expensive.

9.3 Standard Difficulties

  • How should the matrix entries be packed into ciphertext slots?
  • How many rotations are needed to align multiplicands?
  • How many expensive ciphertext-ciphertext multiplications occur?
  • Do we need slot-to-coefficient conversion or ring switching?
  • How many evaluation keys are needed?
A great deal of FHE research is really about finding a better answer to “how do I arrange the data so the costly operations happen less often?”

9.4 Matrix-Native Viewpoints

The recent matrix-arithmetic material you referenced pushes the idea that encrypted objects should be able to represent matrices in a more direct way, rather than forcing everything through vector-slot interpretations that were not designed specifically for large matrix products.

What to watch for in the papers. Look for claims like “matrix multiplication is reduced to a small number of ciphertext multiplications,” “no slot-to-coefficient conversion,” or “native support for matrix transforms.” Those are usually the headline structural gains.

9.5 Where Gentry-Lee Fits in the Matrix Story

This is the right place to connect the abstract Gentry-Lee idea to the actual matrix-arithmetic narrative. Standard FHE systems often handle matrix multiplication by reducing it to a sequence of lower-level ciphertext operations on packed vectors. Gentry-Lee is notable because it pushes toward a representation where matrix multiplication itself is far more central.

The phrase "matrix-native" is the key phrase to remember. It means the encrypted representation is being shaped around the dominant workload instead of forcing the dominant workload to contort itself around an inherited ciphertext format.
Why this matters for private AI. Deep learning workloads are dominated by matrix arithmetic. So if GL reduces the number of awkward transformations, expensive conversions, or auxiliary manipulations needed to do encrypted matrix products, then it can close a very real gap between cryptographic theory and useful machine learning systems.
What to compare when reading GL material. Always compare it against a standard CKKS-style implementation and ask:
  • How many ciphertext multiplications are needed?
  • How many rotations or transpositions are needed?
  • Is slot-to-coefficient conversion avoided?
  • Are matrix transforms supported directly?
  • Does the structure map better to GPU or TPU execution?

Part X: FHE for Machine Learning

10.1 Why ML Is a Natural Target

Many organizations want to run predictions on sensitive data without disclosing the inputs. This is exactly the type of outsourced computation setting where FHE becomes compelling.

10.2 Linear Layers Are Easy Relative to Nonlinearities

Linear algebra is the strong side of many FHE pipelines. Nonlinear activation functions are harder because FHE fundamentally supports addition and multiplication, not arbitrary transcendental functions.

Common trick. Replace a hard activation like ReLU with a low-degree polynomial approximation that can be evaluated homomorphically.

10.3 Inference vs Training

Private inference. Evaluate a trained model on encrypted inputs.
Private training. Update model parameters using encrypted or privacy-sensitive data.
Private inference is already challenging but often feasible. Private training is much harder because it requires many more rounds of high-depth arithmetic.

Part XI: Compiler Systems and HEIR

11.1 Why FHE Needs Compilers

Writing efficient FHE code by hand is extremely difficult. The programmer must reason about arithmetic circuits, depth, layouts, rotations, evaluation keys, approximation error, and backend-specific performance quirks.

FHE compiler. A system that transforms high-level code into an efficient homomorphic evaluation program for a chosen scheme and backend.

11.2 Intermediate Representations

IR. An intermediate representation used inside a compiler to structure program transformations.
MLIR. A modular compiler infrastructure that supports many levels of abstraction through domain-specific dialects.

HEIR is built around the idea that FHE compilation should live in a flexible IR ecosystem rather than inside one monolithic hard-coded compiler.

11.3 What HEIR Tries to Solve

  • Translate high-level tensor or arithmetic programs into FHE-compatible forms.
  • Select a suitable FHE scheme and backend.
  • Choose layouts and kernels.
  • Manage vectorization and batching.
  • Lower the computation into backend-specific encrypted operations.
You can think of HEIR as trying to do for FHE programming what mature compilers did for ordinary hardware programming: make the high-level code less painful without giving up performance.

11.4 Terms You Should Recognize in HEIR Material

Dialect. A family of IR operations for a particular abstraction level.
Lowering. Transforming a higher-level representation into a lower-level one.
Vectorization. Rewriting code so many values are processed in parallel.
Layout optimization. Choosing how logical tensors map into ciphertext structures.
Cost model. A quantitative rule for deciding which implementation strategy is likely cheaper.

Part XII: Hardware, TPU/GPU/CPU, and Systems Concerns

12.1 Why Hardware Matters So Much

FHE is expensive not just because the mathematics is sophisticated, but because ciphertexts are large and the arithmetic is heavy. Memory traffic, parallelism, and kernel quality matter enormously.

12.2 CPU vs GPU vs TPU

CPU. Flexible, general-purpose, often easier for irregular control flow.
GPU. Strong for massive parallel arithmetic on structured workloads.
TPU. Strongly optimized for tensor and matrix-style workloads at scale.
If encrypted computation can be reorganized so that it looks more like dense linear algebra, it becomes more compatible with hardware originally built for AI acceleration.

12.3 Latency, Throughput, Memory

Three systems questions repeatedly appear:

  • How long does one encrypted computation take?
  • How many encrypted computations can run per unit time?
  • How much memory is consumed by ciphertexts and keys?
Common beginner mistake. Looking only at runtime while ignoring key memory and communication cost. In practice, evaluation keys can be huge.

Part XIII: How to Read the Referenced Papers and Videos

13.1 Homomorphic Encryption Intro Material

When an intro video or document says "homomorphic encryption," make sure you extract these points:

  • What operations are supported?
  • What kind of data is represented?
  • What limits the computation?
  • Where does the overhead come from?
  • Why is the scheme still useful despite the overhead?

13.2 HEIR Material

When reading or watching HEIR material, focus less on syntax and more on architecture:

  • What input language is assumed?
  • What IR layers exist?
  • Where are layout decisions made?
  • How is the final backend selected?
  • What kinds of optimization passes are scheme-independent versus scheme-specific?

13.3 Matrix-Arithmetic Papers

When you read the matrix papers, ask the following every time:

  • What encrypted object is being represented?
  • What operations are native?
  • How many ciphertext multiplications are required?
  • How many rotations or key-switches are required?
  • What expensive operations are avoided?
  • Is the gain asymptotic, practical, or both?
  • Is the method better for large matrices, small matrices, or specific shapes?

Part XIV: A Practical Study Roadmap

14.1 Stage 1: Learn the Language

First goal: become fluent in the words. You should be able to explain plaintext, ciphertext, public key, secret key, homomorphic evaluation, noise, depth, bootstrapping, packing, rotation, relinearization, and CKKS out loud without notes.

14.2 Stage 2: Learn the Structural Bottlenecks

Before reading advanced papers, make sure you can answer these:

  • Why does noise grow?
  • Why are multiplications harder than additions?
  • Why do layouts and rotations matter?
  • Why is matrix multiplication such an important benchmark?
  • Why are compilers needed in FHE?

14.3 Stage 3: Learn the Scheme Families

Build a rough map:

  • BFV/BGV: exact arithmetic.
  • CKKS: approximate numeric computing.
  • TFHE family: Boolean / small-integer / LUT-heavy workflows.
  • Matrix-native proposals: redesign around linear algebra itself.

14.4 Stage 4: Learn the Systems Stack

At that point, you are ready to understand the whole chain:

  • High-level model or program.
  • Compiler / IR / layout optimization.
  • Scheme-specific encrypted kernels.
  • Hardware backend.
  • Performance and memory tradeoffs.
Final takeaway. FHE is not just one cryptographic trick. It is a stack. The stack includes cryptographic security assumptions, algebraic representations, noise management, packing strategies, compiler transformations, matrix kernels, and hardware-aware execution. The recent work around encrypted matrix arithmetic and HEIR is exciting precisely because it improves multiple layers of that stack at once.

This page is written for the case where you know essentially nothing about fully homomorphic encryption. The goal is to build the subject from the ground up: what encryption is, why computation on encrypted data is hard, how FHE solves that problem, why noise and bootstrapping appear, how matrix arithmetic fits modern machine learning, and why compiler systems such as HEIR matter for making the whole stack usable.

The emphasis is on conceptual structure. Each section introduces the object, explains why it matters, gives the cleanest mental model available, and highlights the vocabulary you need in order to read papers and watch talks without getting lost.

Part I: Why We Need FHE

1.1 The Basic Problem

Suppose you have sensitive data: medical records, financial transactions, private prompts, model inputs, or enterprise documents. You want some untrusted server to compute on that data for you. Traditional encryption protects the data at rest and in transit, but not during computation. The usual workflow is:

  • Encrypt data locally.
  • Send ciphertext to the server.
  • Server must decrypt to compute.
  • So the server learns the plaintext.
Goal. We want an encryption scheme that allows useful computation directly on ciphertexts, so that the server never sees the underlying plaintext.
FHE is about removing the tension between privacy and usefulness. Ordinary encryption gives privacy but blocks computation. Plain outsourced computation gives usefulness but loses privacy. FHE tries to get both at once.

1.2 The Dream Output Condition

If the plaintext is \(m\), and \(f\) is some function we want to compute, we would like the server to transform an encryption of \(m\) into an encryption of \(f(m)\), without ever learning \(m\) or \(f(m)\).

Correctness pattern. If \(c = \mathrm{Enc}(m)\), the server computes \[ c' = \mathrm{Eval}(f, c), \] and then the client decrypts: \[ \mathrm{Dec}(c') = f(m). \]
Example. A hospital could encrypt patient features, a cloud service could run a risk-scoring model on the encrypted inputs, and only the hospital would learn the final risk score after decryption.

1.3 Four Practical Caveats

The slogan "run programs on encrypted data" is true, but in practice there are four important caveats that shape the entire field.

  • FHE is much slower than ordinary computation.
  • Noise limits the amount of computation unless special techniques are used.
  • Control flow cannot depend on secret data in the usual way.
  • Ciphertexts and evaluation keys can be very large.
Control-flow consequence. If a secret input determined whether the program took a short branch or a long branch, the runtime itself could leak information about the secret. So in secure FHE programming, one often computes all branches and then selects the right result, or one works with fixed upper bounds for loops and iterations.
This is why FHE programs often feel less like ordinary application code and more like carefully scheduled kernels: the shape of the computation has to be mostly fixed in advance.

Part II: Basic Cryptography Background

2.1 Plaintext, Ciphertext, Keys

Plaintext. The original readable data.
Ciphertext. The encrypted form of the data.
Secret key. The private object used to decrypt.
Public key. The public object others can use to encrypt to you.

In public-key encryption, anyone can encrypt to the owner of the secret key, but only the secret-key holder can decrypt.

2.2 Symmetric vs Public-Key Encryption

Symmetric-key encryption. The same shared secret key is used for encryption and decryption.
Public-key encryption. Encryption uses a public key and decryption uses a secret key.
FHE is usually discussed in the public-key setting because outsourcing computation naturally fits the model where many parties encrypt data to one party that owns the decryption key.

2.3 What Security Usually Means

Encryption should hide the plaintext from anyone who does not have the secret key. In modern cryptography, security is expressed as the inability of efficient adversaries to distinguish encryptions of chosen messages.

Important mindset. In cryptography, "secure" does not mean "looks random to me." It means the scheme resists mathematically formal attack models under explicit hardness assumptions.

Part III: The Core Idea of Homomorphic Encryption

3.1 What "Homomorphic" Means

Homomorphism. A structure-preserving map. In this context, operations on ciphertexts correspond to operations on plaintexts.

A toy additive example would satisfy: \[ \mathrm{Dec}(c_1 \oplus c_2) = m_1 + m_2, \] whenever \(c_1 = \mathrm{Enc}(m_1)\) and \(c_2 = \mathrm{Enc}(m_2)\).

3.2 Partial, Somewhat, Leveled, and Fully Homomorphic Encryption

Partially homomorphic encryption. Supports only a restricted class of operations, such as just addition or just multiplication.
Somewhat homomorphic encryption. Supports both addition and multiplication, but only for a limited computation size before decryption fails.
Leveled FHE. Supports all circuits up to a chosen depth bound.
Fully homomorphic encryption. Supports arbitrary bounded computation in principle, because the scheme can refresh ciphertexts as needed.
Key structural difference. The jump from "leveled" to "fully" is bootstrapping. A leveled scheme can only survive a predetermined amount of multiplicative work. A fully homomorphic scheme can repeatedly refresh the ciphertext and continue.

Part IV: Noise, Depth, and Bootstrapping

4.1 Why Noise Appears

Modern lattice-based encryption schemes deliberately add randomness and error terms. This noise is not a bug; it is central to security. But as homomorphic operations are applied, the noise grows.

Noise. A hidden error component inside a ciphertext that must stay within a certain range for decryption to remain correct.
Think of each ciphertext as carrying a "budget." Additions spend a little of it. Multiplications spend much more. When the budget is exhausted, the ciphertext still exists, but it no longer decrypts reliably.

4.2 Multiplicative Depth

Multiplicative depth. The maximum number of multiplications on any path through the arithmetic circuit being evaluated.
Example. The expression \((ab)(cd)\) has multiplicative depth \(2\): first compute \(ab\) and \(cd\), then multiply the results.
Why depth matters more than count. Many FHE costs and parameter choices are driven not by the total number of operations but by how many multiplicative layers are stacked before a refresh.

4.3 Bootstrapping

Bootstrapping. A refresh procedure that reduces the effective noise of a ciphertext so that more homomorphic computation can continue.

Historically, bootstrapping was the key conceptual breakthrough that made fully homomorphic encryption possible.

The slogan is: use encrypted computation to clean up an encrypted ciphertext. It sounds circular at first, but that circularity is exactly the genius of the idea.
Practical consequence. When people say FHE is slow, a large part of that complaint is really about the cost of high-depth operations and bootstrapping.

Part V: Algebra and Linear Algebra Prerequisites

5.1 Why Cryptography Uses Strange Algebra

If you already know matrix multiplication, the biggest shift in cryptography is that we stop working over the ordinary real numbers and start working in more rigid algebraic worlds. These worlds are chosen because they make three things possible at once:

  • Arithmetic can be done efficiently by computers.
  • The structure is rich enough to encode useful computation.
  • Recovering hidden information appears computationally hard.
In linear algebra, the algebraic setting is usually chosen because it models geometry or data. In cryptography, the algebraic setting is often chosen because it creates a controlled mixture of useful structure and computational hardness.

5.2 Modular Arithmetic

FHE schemes are built over arithmetic modulo one or more integers \(q\). To compute modulo \(q\) means we only care about remainders after division by \(q\). Two numbers are treated as equivalent if they differ by a multiple of \(q\).

Congruence modulo \(q\). We write \[ a \equiv b \pmod q \] if \(q\) divides \(a-b\).
Example. Modulo \(7\), one has \(5+4 \equiv 2 \pmod 7\), since \(9\) leaves remainder \(2\) on division by \(7\).
Another example. Modulo \(7\), one has \(6\cdot 6 = 36 \equiv 1 \pmod 7\).
The phrase "wrap around" is accurate. On a clock, \(11+3=2\) if the clock has 12 hours. Modular arithmetic is that same idea, except the modulus \(q\) can be very large and chosen for algorithmic reasons.

5.3 Fields vs Rings

Many students first meet modular arithmetic in settings where everything behaves nicely, especially when the modulus is prime. Cryptography often works in settings that are slightly less nice but much more useful.

Field. A number system where you can add, subtract, multiply, and divide by every nonzero element.
Ring. A set with addition and multiplication, where addition behaves like an abelian group and multiplication distributes over addition, but division by nonzero elements is not generally available.
Field example. \(\mathbb{Z}_7\) is a field because \(7\) is prime, so every nonzero residue has a multiplicative inverse.
Ring example. \(\mathbb{Z}_{8}\) is a ring but not a field. For example, \(2\) has no inverse modulo \(8\).
A ring is "less flexible" than a field, but that extra rigidity is not a problem for cryptography. In fact, many useful cryptographic objects naturally live in rings.

5.4 What \(\mathbb{Z}_q\) Actually Means

The notation \(\mathbb{Z}_q\) means the integers modulo \(q\). Its elements are residue classes, which you can picture concretely as the set \[ \{0,1,2,\dots,q-1\}. \] Arithmetic is done as usual and then reduced modulo \(q\).

Why this matters. When a paper says that a vector has entries in \(\mathbb{Z}_q\), it means each coordinate is only tracked modulo \(q\). So addition and multiplication happen coordinatewise with reduction modulo \(q\).

5.5 Polynomials as Algebraic Containers

A polynomial is an expression like \[ a_0 + a_1X + a_2X^2 + \cdots + a_dX^d. \] In FHE, the coefficients \(a_i\) often live in \(\mathbb{Z}_q\), so all coefficient arithmetic is done modulo \(q\).

Example. Over \(\mathbb{Z}_5\), the polynomials \[ 4 + 3X + X^2 \qquad\text{and}\qquad 2 + 4X \] add to \[ (4+2) + (3+4)X + X^2 \equiv 1 + 2X + X^2 \pmod 5. \]
A polynomial ring lets you package many numbers into one algebraic object. That is one reason it is so natural for batched encrypted computation.

5.6 Quotient Rings and Why \(X^N+1\) Appears

In RLWE-based cryptography, one often works in polynomial rings such as \[ R_q = \mathbb{Z}_q[X]/(X^N+1). \] This notation can look intimidating, but the idea is manageable if you read it in two pieces:

  • \(\mathbb{Z}_q[X]\) means polynomials whose coefficients are in \(\mathbb{Z}_q\).
  • Dividing by \((X^N+1)\) means we identify polynomials that differ by a multiple of \(X^N+1\).
Quotient-ring rule. In \(R_q = \mathbb{Z}_q[X]/(X^N+1)\), we are allowed to replace \(X^N\) by \(-1\).
Example. If \(N=4\), then in this ring, \[ X^4 \equiv -1, \qquad X^5 \equiv -X, \qquad X^6 \equiv -X^2. \] So every polynomial can be reduced to degree at most \(3\).
This means the ring behaves like a fixed-size vector space of dimension \(N\), because every element can be represented by its \(N\) coefficients on \[ 1, X, X^2, \dots, X^{N-1}. \] You can think of a ring element as an \(N\)-dimensional vector with a special multiplication rule.

5.7 Why Polynomial Multiplication Is Interesting

Addition of ring elements is just coefficientwise addition, so it looks like vector addition. Multiplication is more interesting: multiplying polynomials mixes the coefficients together in a structured way.

Example. If \[ a(X)=a_0+a_1X \qquad\text{and}\qquad b(X)=b_0+b_1X, \] then \[ a(X)b(X)=a_0b_0 + (a_0b_1+a_1b_0)X + a_1b_1X^2. \] The coefficients are being convolved together.
This is one reason rings are so useful for cryptography: multiplication is richer than plain coordinatewise multiplication, but still structured enough to implement efficiently.

5.7A DFT and NTT: The Idea

Polynomial multiplication by the schoolbook rule costs quadratic work in the degree. That is too expensive for the large polynomial rings used in RLWE. The main speedup comes from converting multiplication into pointwise multiplication in another domain.

DFT viewpoint. Convolution in coefficient space becomes pointwise multiplication in evaluation space.
Signal-processing analogy. If the coefficient vectors of two polynomials are treated like signals, then polynomial multiplication is a structured convolution. Fourier transforms diagonalize convolution.

5.7B DFT and NTT: The Math

If \[ a(X)=\sum_{i=0}^{N-1} a_iX^i,\qquad b(X)=\sum_{i=0}^{N-1} b_iX^i, \] then the coefficient vector of the product is a convolution of the coefficient vectors of \(a\) and \(b\). Over the complex numbers, the discrete Fourier transform gives \[ \widehat{a \ast b} = \widehat{a}\cdot \widehat{b}, \] where the multiplication on the right is pointwise.

NTT version. The number-theoretic transform is the finite-field or modular-arithmetic analogue of the DFT. Instead of using complex roots of unity, it uses roots of unity inside \(\mathbb{Z}_q\) or a related ring. That makes it suitable for cryptographic arithmetic.
The DFT and NTT do the same structural job. The DFT lives over complex numbers and is great for intuition. The NTT lives over modular rings and is what many real FHE implementations use.

5.7C DFT and NTT: Implementation Shape

The implementation pattern is:

  • transform both coefficient vectors into an evaluation domain,
  • multiply them pointwise,
  • inverse-transform back to coefficient form,
  • apply the appropriate ring reduction.
def poly_mul_via_transform(a, b):
    A = transform(a)          # DFT or NTT
    B = transform(b)
    C = A * B                 # pointwise multiply
    c = inverse_transform(C)
    return ring_reduce(c)
Why hardware people care. This is exactly why NTT engines matter so much in arithmetic FHE accelerators. A large fraction of the total runtime is polynomial multiplication, and a large fraction of that is transform work.

5.7D A JAX-Style DFT Toy Example

For intuition, here is the complex-number version using FFT machinery: 

import jax.numpy as jnp

def poly_mul_fft(a, b):
    size = a.shape[0] + b.shape[0] - 1
    n = 1
    while n < size:
        n *= 2
    A = jnp.fft.fft(a, n=n)
    B = jnp.fft.fft(b, n=n)
    C = A * B
    c = jnp.fft.ifft(C)
    return jnp.rint(jnp.real(c[:size]))
Important distinction. This FFT example is for intuition only. Real NTT-based crypto code avoids floating point and instead works with modular roots of unity so the arithmetic stays exact in the chosen ring.

5.7H A Tiny DFT Walkthrough by Hand

Let us make the transform story concrete. Take the coefficient vectors \[ a = (1,2),\qquad b=(3,4). \] Interpreting these as degree-1 polynomials gives \[ a(X)=1+2X,\qquad b(X)=3+4X. \]

Plain multiplication. \[ (1+2X)(3+4X)=3+10X+8X^2. \] So the coefficient vector of the product is \((3,10,8)\).

Now pad to length \(4\) and evaluate with a 4-point DFT. Let \(\omega = i\), so \[ \omega^0 = 1,\quad \omega^1 = i,\quad \omega^2 = -1,\quad \omega^3 = -i. \] Then \[ \widehat{a} = (a(1), a(i), a(-1), a(-i)) = (3, 1+2i, -1, 1-2i), \] and similarly \[ \widehat{b} = (7, 3+4i, -1, 3-4i). \]

Pointwise multiply. \[ \widehat{c} = \widehat{a}\cdot \widehat{b} = (21,\; (1+2i)(3+4i),\; 1,\; (1-2i)(3-4i)). \] After inverse DFT, this returns the coefficient vector \((3,10,8,0)\), whose nonzero part is exactly the polynomial product.
The DFT is not doing mysterious magic. It is just moving from coefficient coordinates into a coordinate system where convolution becomes pointwise multiplication.

5.7I A Tiny NTT Walkthrough by Hand

Now do the same idea over modular arithmetic. Take modulus \(q=17\) and length \(4\). The element \[ \omega = 4 \] is a primitive 4th root of unity modulo 17, because \[ 4^2 = 16 \equiv -1 \pmod{17}, \qquad 4^4 \equiv 1 \pmod{17}. \]

Reuse \[ a=(1,2,0,0),\qquad b=(3,4,0,0). \] The 4-point NTT evaluates at powers of \(\omega\): \[ 1,\omega,\omega^2,\omega^3 = 1,4,16,13. \] So \[ \widehat{a} = (a(1), a(4), a(16), a(13)) = (3,9,16,10) \pmod{17}, \] and \[ \widehat{b} = (7,2,16,4) \pmod{17}. \]

Pointwise multiply mod 17. \[ \widehat{c} = (3\cdot 7,\; 9\cdot 2,\; 16\cdot 16,\; 10\cdot 4) \equiv (4,1,1,6)\pmod{17}. \] Applying the inverse NTT recovers \[ c=(3,10,8,0)\pmod{17}, \] which again matches the polynomial product coefficients.
This is the same structure as the DFT, but now every operation stays inside modular arithmetic. That is why NTTs are so important for real cryptographic implementations.

5.7J Negacyclic Convolution and \(x^N + 1\)

Standard convolution computes multiplication in an ordinary polynomial ring. FHE often needs negacyclic convolution because the working ring is \[ \mathbb{Z}_q[x]/(x^N+1). \] In that ring, \[ x^N \equiv -1, \qquad x^{N+t} \equiv -x^t. \]

Example. With \(N=4\), \[ x^4 \equiv -1,\quad x^5 \equiv -x,\quad x^6 \equiv -x^2. \] So when high-degree terms wrap around, they come back with a sign flip.

This is exactly why the reduction step after convolution is different from ordinary cyclic convolution. In plain language:

  • ordinary cyclic convolution wraps coefficients back around unchanged,
  • negacyclic convolution wraps them back around with a minus sign.
Implementation consequence. Real NTT-based negacyclic multiplication is often implemented using a transform specially chosen for the \(x^N+1\) modulus, so the sign-flip behavior is built into the transform machinery rather than handled by slow ad hoc postprocessing.

5.7E Residue Number Systems (RNS)

Arithmetic FHE often needs numbers too large for a single machine word. Rather than using slow multi-precision arithmetic everywhere, implementations frequently decompose a large modulus into many smaller coprime moduli.

Residue number system. Represent a large value \(x\) by its residues \[ (x \bmod q_1,\dots,x \bmod q_k) \] for pairwise coprime moduli \(q_i\).
Why it works. By the Chinese Remainder Theorem, if the product \(Q = q_1\cdots q_k\) is large enough, then the residue tuple determines the original value modulo \(Q\). Addition and multiplication can be done entrywise on the residues. 
def rns_add(x_residues, y_residues, moduli):
    return [(x + y) % q for (x, y, q) in zip(x_residues, y_residues, moduli)]

def rns_mul(x_residues, y_residues, moduli):
    return [(x * y) % q for (x, y, q) in zip(x_residues, y_residues, moduli)]
RNS turns one big hard arithmetic problem into many smaller parallel arithmetic problems. That is exactly the kind of structure hardware likes.

5.7F Double-CRT and Evaluation Encodings

Another major idea from the article is that arithmetic FHE often uses two CRT-like decompositions at once.

Double-CRT. One CRT decomposition handles large coefficient moduli via RNS, while another transform-based decomposition represents a polynomial by its evaluations at selected roots of unity.

The evaluation-domain viewpoint is closely tied to DFT/NTT thinking. Instead of storing the plaintext or ciphertext only by polynomial coefficients, one also works with its values at special points. This makes some operations, especially multiplication, much easier.

Coefficient domain is where the polynomial is "written down." Evaluation domain is where multiplication becomes pointwise. Double-CRT says we also decompose the coefficient modulus itself into many small modular channels.

5.7G Gadget Decomposition

Gadget decomposition is an implementation trick that appears all over FHE, especially in key switching and relinearization. The idea is to rewrite large values in a digit basis so that one side of a multiplication is broken into small pieces.

Bit decomposition. One can write \[ b = \sum_{i=0}^{\ell-1} b_i 2^i,\qquad b_i \in \{0,1\}. \] Then \[ ab = \sum_{i=0}^{\ell-1} a\,b_i\,2^i. \]
Why it helps. If noise growth is asymmetric, it can be cheaper to keep one factor small and digit-decomposed, while absorbing the powers of the base elsewhere using precomputed key material.

5.8 Vectors, Matrices, and Ring Elements

Since the referenced material revolves around encrypted matrix arithmetic, you should know:

  • Vector addition and scalar multiplication.
  • Dot products.
  • Matrix addition.
  • Matrix multiplication.
  • Hadamard (entrywise) multiplication.
  • Transpose and conjugate transpose.
Matrix multiplication formula. If \(A \in \mathbb{R}^{m \times n}\) and \(B \in \mathbb{R}^{n \times p}\), then \[ (AB)_{ij} = \sum_{k=1}^{n} A_{ik}B_{kj}. \]
The bridge to cryptography is that a ciphertext is often not "just a number." It is closer to a structured algebraic object, sometimes best viewed as a small tuple of ring elements. The whole game is to make arithmetic on those structured objects correspond to useful arithmetic on the underlying plaintext data.

5.9 The Minimum Lattice Intuition You Need

Most practical FHE is based on lattice problems such as LWE and RLWE. You do not need full lattice theory at the beginning, but you should know the rough picture.

Lattice. A regular grid of points in high-dimensional space generated by integer combinations of basis vectors.
Simple 2D picture. In two dimensions, the ordinary integer grid \[ \{(m,n): m,n \in \mathbb{Z}\} \] is a lattice.
In high dimensions, some lattice problems appear computationally hard. Modern lattice cryptography hides secrets inside linear-algebraic relationships disturbed by small noise.

5.10 LWE and RLWE at a High Level

LWE. Learning With Errors. Roughly: recover a hidden vector \(s\) from noisy linear equations.

A typical LWE sample looks like \[ (\mathbf{a}, b) \qquad\text{with}\qquad b \approx \langle \mathbf{a}, \mathbf{s} \rangle + e \pmod q, \] where \(\mathbf{a}\) is public, \(\mathbf{s}\) is secret, and \(e\) is a small error term.

RLWE. Ring Learning With Errors. The same basic idea as LWE, but with vectors replaced by ring elements and inner products replaced by ring multiplication.
Why the error term matters. Without noise, the equations would often be solvable by standard linear algebra. The small noise is what turns an easy algebra problem into a hard cryptographic one.
This is one of the biggest conceptual differences from ordinary math classes: in cryptography, adding a tiny error is not sloppiness. It is often the source of security.

5.11 Why Ring-LWE Is Attractive for FHE

  • Ring elements can represent many coefficients at once.
  • Polynomial/ring multiplication can be implemented very efficiently.
  • The resulting ciphertexts support rich structured arithmetic.
  • The hardness assumptions are compatible with modern post-quantum cryptography.
Takeaway. RLWE is popular not because mathematicians like complicated notation, but because it gives an unusually strong combination of efficiency, algebraic structure, and believed security.

5.12 What You Actually Need to Remember

For now, the essentials are: arithmetic is done modulo \(q\); ciphertext components often live in polynomial quotient rings; those ring elements behave like fixed-length coefficient vectors with a special multiplication rule; and the security comes from noisy high-dimensional algebraic problems such as LWE and RLWE.

5.13 Constant-Time Arithmetic

Once you move from mathematical definitions to real cryptographic software, one more issue appears immediately: even if the algebra is correct, the implementation can still leak information if its control flow or timing depends on secret data.

Constant-time arithmetic. An implementation style in which the sequence of low-level operations is designed not to depend on secret values in a way that leaks information through timing or related side channels.
The goal is not literally "every input takes exactly the same number of nanoseconds" in all real hardware circumstances. The goal is: do not branch, index memory, or otherwise vary execution in secret-dependent ways that give an attacker information about hidden data.
Why this matters. Suppose an implementation does one thing when a secret coefficient is large and another when it is small. Then an attacker may be able to infer information about that coefficient by observing timing, cache behavior, power draw, or other side effects. This is a classic side-channel problem.

5.14 Why Ring Arithmetic Is a Good Fit for Branch-Free Code

Addition, subtraction, and multiplication in rings are algebraic operations, so they are naturally close to straight-line arithmetic code. That is one reason lattice-crypto kernels often vectorize well.

Coefficientwise addition. If \[ a=(a_0,\dots,a_{N-1}),\qquad b=(b_0,\dots,b_{N-1}), \] then \[ a+b=(a_0+b_0,\dots,a_{N-1}+b_{N-1}), \] followed by reduction modulo \(q\). This is naturally a uniform coordinatewise loop.
A lot of the implementation challenge is not the ring operation itself, but how to do reduction, normalization, and transforms without secret-dependent branching.

5.15 Branchless Modular Reduction

The most common tiny branching hazard appears after modular arithmetic. Suppose we want a value reduced into the standard range \(\{0,1,\dots,q-1\}\). A beginner might write: 

x = x + y
if x >= q:
    x = x - q

That branch can be problematic if \(x\) depends on secret data. The branch-free idea is to compute both pieces arithmetically and use a mask rather than a control-flow split.

Branchless idea. Compute \[ t = x-q, \] then use a mask derived from the sign of \(t\) to decide whether to keep \(x\) or \(t\), without an if statement. 
def reduce_once_branchless(x, q):
    t = x - q
    mask = (t >> 63) & 1        # schematic signed-mask idea
    return t + mask * q
The exact bit trick depends on representation and language, but the pattern is always the same: use arithmetic or bitwise logic to simulate the choice instead of branching on a secret-dependent condition.

5.16 Branchless Selection as a General Pattern

At a higher level, branchless code often relies on the identity \[ \text{select}(b,u,v) = b\,u + (1-b)\,v \] when \(b\in\{0,1\}\), or on an equivalent bitmask formula.

Mask formula. If mask is all ones when a condition is true and all zeros otherwise, then one can write \[ (u \mathbin{\&} \text{mask}) \;|\; (v \mathbin{\&} \sim\text{mask}) \] instead of branching between \(u\) and \(v\).
Cryptographic lesson. This is why people say "avoid secret-dependent branches." The replacement is not "do nothing"; the replacement is to encode the choice into arithmetic or bit operations.

5.17 JAX-Flavored Toy Example

In high-level array code, the same conceptual idea can be written with selection primitives rather than Python control flow: 

import jax.numpy as jnp

def reduce_once_jax(x, q):
    t = x - q
    return jnp.where(t < 0, x, t)
Important caveat. This illustrates the branchless mathematical shape, but high-level JAX code is not by itself a proof of constant-time behavior. Constant-time guarantees are a lower-level systems property, not just a source-code style choice.

5.18 Why This Matters for FHE and RLWE Code

  • Modular arithmetic appears everywhere in lattice cryptography.
  • Polynomial-ring arithmetic is built from huge numbers of coefficient operations.
  • Branchless kernels vectorize better and map better to hardware.
  • Secret-dependent branches can leak information through timing and cache effects.
Takeaway. Yes, ring operations can often be implemented without branching on secret data, and in serious cryptographic code they often should be. This is one of the places where algebra, security, and systems engineering all meet directly.

Part VI: Major FHE Scheme Families

6.1 BFV and BGV

BFV and BGV are classic lattice-based schemes designed for exact arithmetic over integers modulo some value. They are useful when exact combinatorial or modular computation matters.

If your problem really is discrete arithmetic, these schemes feel natural. If your problem looks like floating point machine learning, they are often less natural than CKKS.

6.1A BFV/BGV and the Key-Basis View

A very useful implementation-level picture from the article is to think of a ciphertext as living in a basis built from powers of the secret key.

Degree-1 basis. A ciphertext is often written as a pair \((c_0,c_1)\), and decryption begins by evaluating \[ c_0 + c_1 s, \] where \(s\) is the secret key. So the ciphertext naturally lives in the basis \((1,s)\).

When multiplying \((c_0,c_1)\) and \((b_0,b_1)\), the product becomes \[ (c_0b_0,\; c_0b_1 + c_1b_0,\; c_1b_1), \] which now lives in the basis \((1,s,s^2)\).

Relinearization viewpoint. Relinearization is the process of converting the degree-2 key basis back to the degree-1 basis, typically using special key-switching material involving an encryption of \(s^2\).

6.1B Levels, Modulus Switching, and "More Primes"

Another key point emphasized in the article is that leveled arithmetic FHE often carries a chain of moduli \[ Q_0 \mid Q_1 \mid \cdots \mid Q_L. \] A ciphertext begins at a large top modulus and is gradually switched downward after multiplications.

Each multiplication consumes one "level." Modulus switching reduces both the coefficient modulus and the noise scale, letting a deep circuit survive without bootstrapping.
Engineering slogan. Got multiplicative depth? You need more primes.

6.2 CKKS

CKKS. An approximate homomorphic encryption scheme designed for efficient arithmetic on vectors of approximate real or complex values.

CKKS is widely used in private inference because neural-network workloads naturally tolerate approximation.

Why CKKS is popular in ML. Neural networks already operate with floating-point approximations, quantization, and numerical tolerance. An approximate encryption scheme fits that culture much better than a strictly exact one.

6.2A CKKS Scales and Precision

The article also stresses an important usability point: CKKS users do not only track noise, but also precision and scale.

Scale. A factor attached to a CKKS ciphertext that determines how the encoded approximate real values are represented internally.

After multiplication, scales multiply too, so CKKS applies a rescaling operation to bring the representation back under control. This also drops some low-order precision.

In BGV/BFV you worry mainly about correctness and noise. In CKKS you also worry about numerical analysis.

6.3 TFHE-Style Schemes

TFHE-family schemes are often optimized for Boolean or small-integer operations and for very fast bootstrapping at the level of bits, gates, or lookup-table style operations.

CKKS is often the "linear algebra" scheme. TFHE is often the "logic / programmable bootstrapping / LUT" scheme. That is an oversimplification, but it is a useful first approximation.

6.3A CGGI / TFHE and Programmable Bootstrapping

The article's treatment of CGGI adds an important idea we did not spell out enough before: bootstrapping can do extra work besides refreshing noise.

Programmable bootstrapping. A bootstrapping procedure that both refreshes a ciphertext and applies a chosen function to the encrypted message at the same time.

For very small message spaces, the function can be represented as a lookup table.

Lookup-table view. If the encrypted message is an \(m\)-bit integer, then a univariate function can be represented by a table of size \(2^m\).
Why boolean FHE likes this. Comparisons, max/min, bitwise logic, and many short-integer operations become natural when you can cheaply apply small lookup tables during bootstrapping.

6.3B Blind Rotation as the Inner Mechanism

The article peeks inside programmable bootstrapping and notes that, very roughly, a lookup table is represented in an RLWE ciphertext and then blindly rotated by an encrypted amount.

The point is not that the server sees the rotation amount; it does not. The point is that the encrypted message controls which part of the table becomes aligned with the output position.

6.3C Scheme Switching

A major newer trend emphasized in the article is that FHE schemes are no longer totally isolated islands.

Scheme switching. Converting a ciphertext from one FHE scheme to another so different parts of a program can be evaluated in the scheme best suited to each subtask.
Hybrid idea. Use CKKS for large SIMD arithmetic, use CGGI for branching-heavy or low-precision logic, and switch between them when needed.

6.4 Why New Matrix-Native Schemes Matter

The referenced matrix-arithmetic work is exciting because standard FHE schemes were not originally designed around matrix multiplication as the first-class primitive, even though matrix multiplication dominates modern ML.

Main systems insight. If the dominant workload is matrix arithmetic, then it can be worth redesigning the cryptographic representation so that matrix operations become native rather than awkwardly emulated.

6.5 Gentry-Lee and the GL Direction

The Gentry-Lee direction, often referred to informally as the GL scheme in recent talks and summaries, is important because it pushes this matrix-native viewpoint much more aggressively than traditional FHE pipelines.

High-level idea. Instead of treating matrix arithmetic as something that must be assembled out of vector-slot tricks, the Gentry-Lee approach aims to make matrix operations themselves much more natural inside the encrypted representation.

You should think of GL not merely as "another FHE scheme," but as part of a design shift. Traditional FHE systems often begin with a ciphertext model optimized for scalar or vector arithmetic, and then build matrix multiplication indirectly. The Gentry-Lee perspective asks whether the representation itself should be redesigned around matrix workloads from the start.

If modern private AI spends most of its time doing matrix multiplication, then a scheme built around matrix arithmetic may be a better fit than a scheme that only becomes matrix-friendly after many layout conversions and auxiliary operations.

GL starts from the workload we actually care about: matrix arithmetic.

6.6 How GL Differs from the Usual CKKS Mental Model

In the usual CKKS mental model, you pack many values into slots of a ciphertext, then spend substantial effort arranging, rotating, summing, converting, and aligning those slots so the desired linear algebra happens.

CKKS-style mindset. Start with packed vectors, then engineer matrix arithmetic by clever slot layout, rotations, rescaling, and kernel design.
GL-style mindset. Start by asking how matrices themselves should live inside ciphertexts so that matrix operations are closer to native operations of the scheme.
Conceptual contrast. CKKS is excellent and broadly useful, but its native abstraction is not "encrypted matrix" in the strongest sense. The GL direction is exciting because it tries to reduce that mismatch between the algebraic object used by the scheme and the algebraic object used by the application.

6.8 A Mathematical Walkthrough of the GL Viewpoint

What follows is the right beginner mathematical model to keep in your head. It is a schematic walkthrough of the GL direction rather than a claim that every implementation detail below is the literal public specification of the scheme. The point is to understand the math the scheme is trying to optimize.

Target plaintext object. Instead of thinking of the plaintext as a single scalar or a packed vector, think of it as a matrix \[ M \in R^{n \times n} \] over some ring \(R\), often itself derived from modular or polynomial arithmetic.

The dream is to have an encryption map \[ \mathsf{Enc}: R^{n \times n} \to \mathcal{C} \] from plaintext matrices into a ciphertext space \(\mathcal{C}\), together with a homomorphic evaluation rule satisfying \[ \mathsf{Dec}(\mathsf{Eval}(\otimes, \mathsf{Enc}(A), \mathsf{Enc}(B))) = AB \] for matrix multiplication.

The entire GL motivation can be summarized this way: if the application wants matrix multiplication, then the encrypted algebra should try to make encrypted matrix multiplication look like matrix multiplication, rather than making it look like an awkward simulation built from slot shuffles.

Idea:

The encrypted interface should preserve the shape of the mathematical operation.

Math:

\[ \mathsf{Dec}(\mathsf{Eval}(\otimes,\mathsf{Enc}(A),\mathsf{Enc}(B))) = AB. \]

6.9 The Standard CKKS Reduction Versus the GL Goal

In a CKKS-style system, a matrix \(A\) is usually encoded into one or more packed ciphertexts. The real work is then to engineer \[ C = AB \] by translating matrix multiplication into a sequence of slotwise operations, rotations, and accumulations. One can view this as replacing a clean algebraic identity by a long implementation identity: \[ AB \quad\leadsto\quad \text{pack}(A), \text{pack}(B), \text{rotate}, \text{multiply}, \text{sum}, \text{rescale}, \dots \]

Core mismatch. Matrix multiplication is bilinear: \[ (A+B)C = AC + BC, \qquad A(B+C)=AB+AC, \] and its entries are defined by inner products: \[ (AB)_{ij} = \sum_{k=1}^{n} A_{ik}B_{kj}. \] A scheme optimized around packed vectors must reconstruct this bilinear structure indirectly. The GL goal is to move more of this bilinear structure into the native encrypted algebra itself.

Idea:

The important structure is not just "multiply numbers," but bilinearity across rows and columns.

Math:

\[ (AB)_{ij} = \sum_{k=1}^{n} A_{ik}B_{kj}. \]

In JAX:

    return jnp.sum(A[i, :] * B[:, j])

6.10 The Algebraic Shape You Should Imagine

The cleanest abstract model is that a ciphertext represents a matrix-valued plaintext plus hidden noise: \[ \widetilde{A} = A + E_A, \qquad \widetilde{B} = B + E_B, \] where \(A,B\) are the intended plaintext matrices and \(E_A, E_B\) are encrypted error objects that remain hidden from the evaluator.

Then the homomorphic multiplication should behave schematically like \[ \widetilde{A}\widetilde{B} = (A+E_A)(B+E_B) = AB + AE_B + E_AB + E_AE_B. \] The cryptographic problem is to ensure that the non-\(AB\) terms remain controlled enough that decryption still recovers \(AB\) correctly.

This is the matrix version of the standard FHE story: useful structure plus controlled error. The difference is that the useful structure is now oriented around matrix algebra, not just scalar or packed-vector arithmetic.

Idea:

Ciphertexts should be thought of as structured objects carrying hidden data plus noise.

Math:

\[ \widetilde{A}\widetilde{B} = AB + AE_B + E_AB + E_AE_B. \]

In Ciphertext Code:

6.11 Why Matrix-Native Structure Can Lower Cost

Suppose a traditional packed-vector implementation requires:

  • several ciphertext-ciphertext products,
  • many rotations,
  • layout conversions,
  • and expensive coefficient/slot rearrangements.

A matrix-native scheme tries to compress the same mathematical objective into something closer to: \[ \mathsf{Enc}(A), \mathsf{Enc}(B) \quad\mapsto\quad \mathsf{Enc}(AB) \] with fewer auxiliary transformations.

Idealized comparison. If a CKKS-style method says "perform matrix multiplication by decomposing it into many packed-vector kernels," then the GL aspiration is "make the matrix product itself the kernel."
What the speedup is really about. The gain is not magical. The gain comes from reducing the number of expensive secondary operations needed to force the ciphertext representation to imitate matrix algebra.

The goal is fewer auxiliary operations between input matrices and output matrix.

Math:

\[ \mathsf{Enc}(A),\mathsf{Enc}(B)\mapsto \mathsf{Enc}(AB). \]

Part VII: The Standard FHE Operations Vocabulary

7.1 Addition and Multiplication

Every practical FHE user needs to distinguish plaintext-ciphertext operations from ciphertext-ciphertext operations. The latter are usually much more expensive.

Cheaper pattern. Multiply an encrypted vector by a known public constant matrix.
Harder pattern. Multiply an encrypted matrix by another encrypted matrix.

7.2 Relinearization

Relinearization. A post-multiplication procedure that compresses a larger ciphertext form back into the standard ciphertext size.
Multiplication often makes ciphertexts algebraically “fatter.” Relinearization shrinks them back into the normal format, at a cost.

7.3 Key Switching and Rotation Keys

Key switching. Transforming a ciphertext under one effective key representation into a ciphertext under another, without decryption.

Many operations such as rotations require auxiliary evaluation keys. These keys improve capability but increase memory usage.

7.4 Modulus Switching and Rescaling

In exact schemes, modulus switching helps manage noise. In CKKS, rescaling additionally manages the scale attached to approximate encodings after multiplication.

Important distinction. Newcomers often mix up “noise management” and “precision management.” In CKKS, rescaling is tied to both.

Part VIII: Packing, Slots, and SIMD

8.1 Why Packing Exists

FHE would be nearly unusable if each ciphertext carried only one scalar. Modern schemes therefore pack many values into one ciphertext and apply the same operation to all of them simultaneously.

Slots. The packed components of a ciphertext that can often be manipulated in SIMD style.
SIMD. Single instruction, multiple data: one operation acts on many packed values at once.

8.2 Rotations

Packed computation is powerful only if we can move data around inside the packed layout. Rotations shift slot positions so that different values can interact.

Example. A dot product can be implemented by elementwise multiplication followed by a sequence of rotations and additions that sum the coordinates.

8.3 Layout Matters

In FHE, performance often depends less on the abstract mathematics of the computation and more on how the data is arranged in ciphertext slots. Good layout can save huge numbers of rotations and key-switches.

Part IX: Matrix Arithmetic Under Encryption

9.1 Why Matrix Multiplication Is Central

Matrix multiplication is the computational engine of much of scientific computing and machine learning. If you can do encrypted matrix multiplication efficiently, you unlock a large fraction of the useful workload.

Systems principle. Since neural networks are dominated by linear layers, attention projections, and other tensor contractions, the efficiency of encrypted matrix multiplication often determines whether private AI is viable at all.

9.2 Plaintext-Ciphertext vs Ciphertext-Ciphertext Matrix Multiplication

Plaintext-ciphertext multiplication. One matrix is public/known; the other is encrypted.
Ciphertext-ciphertext multiplication. Both matrices are encrypted.

The second problem is conceptually cleaner from a privacy perspective, but also much harder and more expensive.

9.3 Standard Difficulties

  • How should the matrix entries be packed into ciphertext slots?
  • How many rotations are needed to align multiplicands?
  • How many expensive ciphertext-ciphertext multiplications occur?
  • Do we need slot-to-coefficient conversion or ring switching?
  • How many evaluation keys are needed?
A great deal of FHE research is really about finding a better answer to “how do I arrange the data so the costly operations happen less often?”

9.4 Matrix-Native Viewpoints

The recent matrix-arithmetic material you referenced pushes the idea that encrypted objects should be able to represent matrices in a more direct way, rather than forcing everything through vector-slot interpretations that were not designed specifically for large matrix products.

What to watch for in the papers. Look for claims like “matrix multiplication is reduced to a small number of ciphertext multiplications,” “no slot-to-coefficient conversion,” or “native support for matrix transforms.” Those are usually the headline structural gains.

9.5 Where Gentry-Lee Fits in the Matrix Story

This is the right place to connect the abstract Gentry-Lee idea to the actual matrix-arithmetic narrative. Standard FHE systems often handle matrix multiplication by reducing it to a sequence of lower-level ciphertext operations on packed vectors. Gentry-Lee is notable because it pushes toward a representation where matrix multiplication itself is far more central.

The phrase "matrix-native" is the key phrase to remember. It means the encrypted representation is being shaped around the dominant workload instead of forcing the dominant workload to contort itself around an inherited ciphertext format.
Why this matters for private AI. Deep learning workloads are dominated by matrix arithmetic. So if GL reduces the number of awkward transformations, expensive conversions, or auxiliary manipulations needed to do encrypted matrix products, then it can close a very real gap between cryptographic theory and useful machine learning systems.

Idea:

A matrix-first representation is valuable because ML workloads are matrix-first workloads.

Math:

\[ y = Wx + b,\qquad C = AB. \]

9.6 A Worked Mathematical Comparison

Let \[ A,B \in R^{n \times n}. \] The plaintext goal is to compute \[ C = AB, \qquad C_{ij} = \sum_{k=1}^{n} A_{ik}B_{kj}. \] This formula already tells you what any encrypted implementation must somehow reproduce.

Naive scalar view. If each entry were encrypted separately, then computing one output entry \(C_{ij}\) would require \(n\) encrypted multiplications and \(n-1\) encrypted additions. Computing the whole matrix would therefore require \(n^3\) scalar products plus many additions.

Packed-vector FHE improves on this by evaluating many such products in parallel, but the evaluator then pays for the privilege through nontrivial data motion. In effect, the algorithm must repeatedly answer:

Alignment problem. How do we move the encrypted data so that \(A_{ik}\) and \(B_{kj}\) land in positions where a single ciphertext operation can combine them?

That is why rotations appear. The underlying matrix formula has an index \(k\) that must be summed over. Packed FHE implementations often realize that sum by repeatedly aligning the \(k\)-th pieces and adding them up.

The mathematics of matrix multiplication is simple. The engineering difficulty is that ciphertext layouts do not naturally present row \(i\) of \(A\) and column \(j\) of \(B\) to each other in the right way.

9.7 The GL Hope in Formula Form

A matrix-native scheme aims to represent the encrypted object so that the bilinear map \[ (A,B)\mapsto AB \] is reflected more directly in ciphertext space. In the best conceptual case, one imagines an encrypted product rule \[ \mathsf{Enc}(A)\star\mathsf{Enc}(B) \approx \mathsf{Enc}(AB), \] where \(\star\) is a ciphertext operation aligned with matrix multiplication itself.

The "\(\approx\)" is important. In lattice-based cryptography, encrypted computation is never exact in the naive sense; there is always hidden structured error. A more realistic schematic identity is \[ \mathsf{Enc}(A)\star\mathsf{Enc}(B) = \mathsf{Enc}(AB) + \text{controlled noise terms}. \]

Why this is powerful. If the native ciphertext algebra already mirrors matrix multiplication, then much of the usual index-bookkeeping disappears. The evaluator no longer spends as much effort translating matrix algebra into slot algebra.

Idea:

The scheme should lower from mathematical matrix algebra to ciphertext operations with less translation work.

Math:

\[ \mathsf{Enc}(A)\star\mathsf{Enc}(B)\approx \mathsf{Enc}(AB). \]

In HEIR/OpenFHE Lowering:

%0 = openfhe.mul_no_relin %arg0, %arg1, %arg2
%1 = openfhe.relin %arg0, %0
%2 = openfhe.rot %arg0, %1 {static_shift = 4 : index}
%3 = openfhe.add %arg0, %1, %2
What to look for in a paper claim. If a GL-style paper says it uses only a small number of ciphertext multiplications to realize a large matrix product, the mathematical claim is that the ciphertext representation already encodes a large amount of bilinear structure that CKKS-style implementations often have to reconstruct manually.

9.8 Hardware Interpretation

This math viewpoint also explains the hardware excitement. TPUs and GPUs are strong when the core workload looks like dense linear algebra: \[ C = AB, \qquad y = Wx, \qquad X^\top X, \quad \text{etc.} \] If the encrypted primitive is itself closer to matrix multiplication, then the software stack has a better chance of mapping onto those accelerators efficiently.

Big picture. The GL story is not "we found a faster trick." It is closer to "we changed the algebraic representation so that the dominant computation in private AI better matches both the ciphertext mathematics and the accelerator hardware."

Part X: FHE for Machine Learning

10.1 Why ML Is a Natural Target

Many organizations want to run predictions on sensitive data without disclosing the inputs. This is exactly the type of outsourced computation setting where FHE becomes compelling.

10.2 Linear Layers Are Easy Relative to Nonlinearities

Linear algebra is the strong side of many FHE pipelines. Nonlinear activation functions are harder because FHE fundamentally supports addition and multiplication, not arbitrary transcendental functions.

Common trick. Replace a hard activation like ReLU with a low-degree polynomial approximation that can be evaluated homomorphically.

10.3 Inference vs Training

Private inference. Evaluate a trained model on encrypted inputs.
Private training. Update model parameters using encrypted or privacy-sensitive data.
Private inference is already challenging but often feasible. Private training is much harder because it requires many more rounds of high-depth arithmetic.

10.4 Writing FHE Programs Feels Like Writing Kernels

Another valuable point from the article is that writing FHE programs today still feels much more like writing specialized kernels than writing ordinary application code.

Arithmetic FHE rule. You avoid operations that are not polynomial, or you replace them with low-degree polynomial approximations.
Boolean FHE rule. You quantize aggressively and keep bit widths small so lookup tables and bootstrap-heavy circuits remain feasible.
This is one reason compilers matter so much. The programming model is still too manual for most people.

Part XI: Compiler Systems and HEIR

11.1 Why FHE Needs Compilers

Writing efficient FHE code by hand is extremely difficult. The programmer must reason about arithmetic circuits, depth, layouts, rotations, evaluation keys, approximation error, and backend-specific performance quirks.

FHE compiler. A system that transforms high-level code into an efficient homomorphic evaluation program for a chosen scheme and backend.

11.2 Intermediate Representations

IR. An intermediate representation used inside a compiler to structure program transformations.
MLIR. A modular compiler infrastructure that supports many levels of abstraction through domain-specific dialects.

HEIR is built around the idea that FHE compilation should live in a flexible IR ecosystem rather than inside one monolithic hard-coded compiler.

11.3 What HEIR Tries to Solve

  • Translate high-level tensor or arithmetic programs into FHE-compatible forms.
  • Select a suitable FHE scheme and backend.
  • Choose layouts and kernels.
  • Manage vectorization and batching.
  • Lower the computation into backend-specific encrypted operations.
You can think of HEIR as trying to do for FHE programming what mature compilers did for ordinary hardware programming: make the high-level code less painful without giving up performance.

11.4 Terms You Should Recognize in HEIR Material

Dialect. A family of IR operations for a particular abstraction level.
Lowering. Transforming a higher-level representation into a lower-level one.
Vectorization. Rewriting code so many values are processed in parallel.
Layout optimization. Choosing how logical tensors map into ciphertext structures.
Cost model. A quantitative rule for deciding which implementation strategy is likely cheaper.

12.1 Why Hardware Matters So Much

FHE is expensive not just because the mathematics is sophisticated, but because ciphertexts are large and the arithmetic is heavy. Memory traffic, parallelism, and kernel quality matter enormously.

12.4 Pet Examples in JAX

JAX is a nice language for "thinking in kernels" because it makes dense numerical structure very explicit. These examples are not encrypted implementations. They are small plain-text models of the kinds of linear algebra and transformations that FHE systems, FHE compilers, and accelerator mappings care about.

Why JAX is relevant here. JAX provides a NumPy-style array API and transformation tools such as jit and vmap, which makes it a convenient way to express matrix-centric workloads that later motivate FHE compilation and hardware-aware optimization.

12.5 Pet Example 1: Plain Matrix Multiplication

Start with the ordinary matrix product \[ C = AB, \qquad C_{ij} = \sum_{k=1}^{n} A_{ik}B_{kj}. \] In JAX, this is exactly what you would expect: 

import jax
import jax.numpy as jnp

A = jnp.array([[1., 2.],
               [3., 4.]])
B = jnp.array([[5., 6.],
               [7., 8.]])

C = A @ B
print(C)
# [[19. 22.]
#  [43. 50.]]
This is the baseline picture. A matrix-native FHE scheme is exciting precisely because it tries to preserve this clean "write down the matrix product directly" viewpoint for encrypted computation too.

12.6 Pet Example 2: Compiled Matrix Multiplication

JAX can compile a numerical function so it runs more like a backend kernel: 

@jax.jit
def matmul_fn(A, B):
    return A @ B

C = matmul_fn(A, B)
FHE analogy. The source-level function is still "matrix multiply," but a compiler lowers it to a much more optimized backend-specific execution plan. This is conceptually similar to what HEIR tries to do for encrypted programs.

12.7 Pet Example 3: Batched Matrix Multiplication

Many ML workloads are really batches of matrix multiplications: \[ C_b = A_bB_b, \qquad b = 1,\dots,B. \] JAX expresses this naturally: 

A_batch = jnp.arange(2 * 2 * 2, dtype=jnp.float32).reshape(2, 2, 2)
B_batch = jnp.arange(2 * 2 * 2, dtype=jnp.float32).reshape(2, 2, 2)

C_batch = jnp.matmul(A_batch, B_batch)
print(C_batch.shape)
# (2, 2, 2)
This matters because "one ciphertext encodes many things at once" is a recurring FHE idea. Batched JAX code is a good mental warmup for batched encrypted computation, even though the actual mechanisms differ.

12.8 Pet Example 4: Vectorizing a Small Kernel with vmap

Sometimes we define a small operation once and then lift it across many inputs: 

def row_dot(row, x):
    return jnp.dot(row, x)

W = jnp.array([[1., 0., 1.],
               [0., 1., 1.],
               [1., 1., 0.]])
x = jnp.array([2., 3., 5.])

y = jax.vmap(row_dot, in_axes=(0, None))(W, x)
print(y)
# [7. 8. 5.]
Why this is useful. This is mathematically the same as the matrix-vector product \(y = Wx\), but written as a lifted per-row kernel. Compiler systems often move back and forth between these equivalent viewpoints.

12.9 Pet Example 5: Polynomial Multiplication as Convolution

Since FHE lives in polynomial rings, it helps to see polynomial multiplication in code too. If \[ a(X)=a_0+a_1X+\cdots+a_dX^d, \qquad b(X)=b_0+b_1X+\cdots+b_eX^e, \] then multiplying them corresponds to coefficient convolution. 

a = jnp.array([1., 2., 3.])   # 1 + 2X + 3X^2
b = jnp.array([4., 5.])      # 4 + 5X

c = jnp.convolve(a, b)
print(c)
# [ 4. 13. 22. 15.]
Math check. Indeed, \[ (1+2X+3X^2)(4+5X)=4+13X+22X^2+15X^3. \] This is a good plain-language bridge from ordinary coding to the ring arithmetic underlying RLWE-style schemes.

12.10 Pet Example 6: Negacyclic Reduction

In a ring like \[ R_q = \mathbb{Z}_q[X]/(X^N+1), \] we use the rule \(X^N \equiv -1\). Here is a toy JAX helper that multiplies coefficient vectors and then folds them back into degree less than \(N\) using that negacyclic rule: 

def negacyclic_mul_branchfree(a, b, N):
    raw = jnp.convolve(a, b)
    idx = jnp.arange(raw.shape[0])
    sign = jnp.where(idx < N, 1, -1)
    wrapped_idx = idx % N
    weighted = raw * sign
    out = jnp.zeros((N,), dtype=raw.dtype)
    return out.at[wrapped_idx].add(weighted)

a = jnp.array([1., 2., 0., 0.])   # 1 + 2X
b = jnp.array([3., 1., 0., 0.])   # 3 + X
print(negacyclic_mul_branchfree(a, b, 4))
# corresponds to (1 + 2X)(3 + X) modulo X^4 + 1
This is still a toy, but it is much closer to cryptographic math than ordinary dense linear algebra. It shows how polynomial-ring rules change the multiplication law itself.

12.11 Pet Example 7: Rotate-and-Sum

One common packed-FHE pattern is "multiply coordinatewise, then rotate and sum." In plain JAX, you can model that kind of data motion with array rolls: 

def rotate_and_sum(x):
    y = x
    y = y + jnp.roll(y, 1)
    y = y + jnp.roll(y, 2)
    return y

x = jnp.array([1., 2., 3., 4.])
print(rotate_and_sum(x))
FHE connection. In packed schemes, rotations are expensive because they are not just array indexing tricks; they require special evaluation keys and nontrivial ciphertext transformations. Seeing the rotate-and-sum pattern in plain JAX helps you recognize why layout optimization matters so much.

12.12 Pet Example 8: A Toy Linear Layer

A single neural-network linear layer is just \[ y = Wx + b. \] In JAX: 

def linear_layer(W, x, b):
    return W @ x + b

W = jnp.array([[1., -1., 0.],

Bottom line. These are not encrypted algorithms, but they are the right pet examples for building intuition. They show the algebraic patterns that FHE schemes and FHE compilers are trying to preserve, compress, or accelerate.

The next step is to put the three views next to each other. For each mini-example below, read in this order: first the idea, then the equation, then the code. That habit is exactly what helps when reading FHE papers or compiler systems work.

12.15 Side-by-Side Example A: Matrix-Vector Product

Idea:

A linear layer or a row-by-row scoring rule takes a matrix \(W\) and a vector \(x\), then forms a new vector by dotting each row of \(W\) with \(x\).

Math:

\[ y = Wx, \qquad y_i = \sum_{j=1}^{n} W_{ij}x_j. \]

In JAX:

W = jnp.array([[1., 0., 1.],
               [0., 1., 1.],
               [1., 1., 0.]])
x = jnp.array([2., 3., 5.])

y = W @ x
print(y)
# [7. 8. 5.]
In FHE language, this is the kind of structured bilinear computation you want to preserve under encryption. Matrix-native schemes try to keep this expression close to its original algebraic form.

12.16 Side-by-Side Example B: Polynomial Multiplication

Idea:

Multiply two polynomials by combining every coefficient of the first with every coefficient of the second. This is exactly coefficient convolution.

Math:

If \[ a(X)=\sum_i a_iX^i,\qquad b(X)=\sum_j b_jX^j, \] then \[ a(X)b(X)=\sum_k \left(\sum_{i+j=k} a_i b_j\right)X^k. \]

In JAX:

a = jnp.array([1., 2., 3.])   # 1 + 2X + 3X^2
b = jnp.array([4., 5.])      # 4 + 5X

c = jnp.convolve(a, b)
print(c)
# [ 4. 13. 22. 15.]
Connection to cryptography. RLWE-style schemes live in polynomial quotient rings, so this is much closer to actual cryptographic arithmetic than ordinary floating-point matrix code.

12.17 Side-by-Side Example C: Negacyclic Reduction

Idea:

In a quotient ring like \(\mathbb{Z}_q[X]/(X^N+1)\), high powers of \(X\) are folded back using the rule \(X^N \equiv -1\). So polynomial multiplication is followed by a structured reduction step.

Math:

\[ X^N \equiv -1, \qquad X^{N+t} \equiv -X^t. \] So coefficients past degree \(N-1\) wrap back with a sign flip.

In JAX:

def negacyclic_mul_branchfree(a, b, N):
    raw = jnp.convolve(a, b)
    idx = jnp.arange(raw.shape[0])
    sign = jnp.where(idx < N, 1, -1)
    wrapped_idx = idx % N
    weighted = raw * sign
    out = jnp.zeros((N,), dtype=raw.dtype)
    return out.at[wrapped_idx].add(weighted)
This is the point where ordinary algebra starts to look like cryptographic algebra. You are no longer just multiplying arrays; you are multiplying inside a chosen ring.

12.18 Side-by-Side Example D: Rotate-and-Sum

Idea:

Packed FHE often computes many values in parallel, then rotates the packed data to align terms that need to be added together.

Math:

If a packed vector is \(x=(x_0,\dots,x_{n-1})\), then a rotate-and-sum pattern tries to form expressions like \[ x + \rho(x) + \rho^2(x) + \cdots \] where \(\rho\) denotes a slot rotation.

In JAX:

def rotate_and_sum(x):
    y = x
    y = y + jnp.roll(y, 1)
    y = y + jnp.roll(y, 2)
    return y

x = jnp.array([1., 2., 3., 4.])
print(rotate_and_sum(x))
Why the code matters. In JAX this looks cheap because roll is just an array operation. In packed FHE, the corresponding rotation is cryptographically expensive. That gap is exactly why layout optimization is such a big deal.

12.19 Side-by-Side Example E: Matrix Multiplication and the GL Dream

Idea:

GL aims for an encrypted algebra where matrix multiplication is closer to a native operation, rather than a long recipe built from slot tricks.

Math:

Plaintext target: \[ C = AB. \] Ideal encrypted goal: \[ \mathsf{Enc}(A)\star\mathsf{Enc}(B)\approx \mathsf{Enc}(AB). \]

In JAX:

@jax.jit
def plain_matmul(A, B):
    return A @ B
The plain JAX kernel is what you wish encrypted computation could feel like. The whole GL story is that the ciphertext structure should move closer to this clean mathematical interface.

12.20 Toy Ciphertext Exposure in Code

You asked to see some ciphertext exposure in code. The example below is not a secure cryptosystem. It is a didactic wrapper whose job is only to expose the shape of ciphertext-centric programming: encrypted objects carry hidden values plus metadata such as a noise budget, and homomorphic operations update both. 

from dataclasses import dataclass
import jax.numpy as jnp

@dataclass
class ToyCiphertext:
    payload: jax.Array
    noise_budget: float
    label: str = "ct"

def toy_encrypt(x, *, noise_budget=100.0, label="ct"):
    return ToyCiphertext(payload=jnp.array(x), noise_budget=noise_budget, label=label)

def toy_decrypt(ct: ToyCiphertext):
    return ct.payload

def toy_add(ct1: ToyCiphertext, ct2: ToyCiphertext):
    return ToyCiphertext(
        payload=ct1.payload + ct2.payload,
        noise_budget=min(ct1.noise_budget, ct2.noise_budget) - 1.0,
        label=f"({ct1.label}+{ct2.label})",
    )

def toy_matmul(ct1: ToyCiphertext, ct2: ToyCiphertext):
    return ToyCiphertext(
        payload=ct1.payload @ ct2.payload,
        noise_budget=min(ct1.noise_budget, ct2.noise_budget) - 12.0,
        label=f"({ct1.label}@{ct2.label})",
    )

Idea:

A ciphertext is not just a number. It is an object that stores encrypted content together with hidden algebra and operational constraints.

Math:

Schematic encrypted multiplication: \[ \widetilde{A}\widetilde{B} = AB + \text{noise terms}. \] Operationally, the usable noise budget decreases after multiplication.

In Ciphertext Code:

In the toy wrapper, payload stands in for the hidden encrypted content, and noise_budget stands in for the amount of remaining safe computation.

12.21 Toy Ciphertext Matrix Example

Now we can write code that at least looks like ciphertext-level matrix programming: 

A = toy_encrypt([[1., 2.],
                 [3., 4.]], label="A")
B = toy_encrypt([[5., 6.],
                 [7., 8.]], label="B")

C = toy_matmul(A, B)

print(C.label)
# (A@B)
print(C.noise_budget)
# 88.0
print(toy_decrypt(C))
# [[19. 22.]
#  [43. 50.]]
This is the first step toward reading real FHE code. In actual libraries, the payload would be genuinely encrypted, the budget logic would be tied to precise scheme mathematics, and operations like rotation, relinearization, rescaling, or bootstrapping would show up explicitly.

12.22 Toy Ciphertext Rotation Exposure

Packed schemes also have ciphertext-level transforms that are not plain arithmetic. Here is a toy rotation: 

def toy_rotate(ct: ToyCiphertext, shift: int):
    return ToyCiphertext(
        payload=jnp.roll(ct.payload, shift),
        noise_budget=ct.noise_budget - 3.0,
        label=f"rot({ct.label},{shift})",
    )

v = toy_encrypt([1., 2., 3., 4.], label="v")
v_rot = toy_rotate(v, 1)
print(v_rot.label)
# rot(v,1)
print(toy_decrypt(v_rot))
# [4. 1. 2. 3.]
Why this is pedagogically useful. Real FHE code often has operations whose mathematical role is "just rotate the packed data," but whose cryptographic cost is substantial. Seeing them as first-class methods on ciphertext objects helps build the right mental model.

12.23 What This Toy Model Gets Right and Wrong

  • Right: ciphertexts are objects, not plain arrays.
  • Right: homomorphic operations consume a limited resource such as noise budget.
  • Right: matrix multiplication and rotation are distinct ciphertext operations.
  • Wrong: the toy wrapper is not secure, not parameterized like a real scheme, and not mathematically faithful in its noise accounting.
  • Wrong: real FHE libraries expose many more details, including keys, evaluation keys, scales, levels, and backend-specific representations.
Best way to use this section. Treat the JAX examples as the plain mathematical target, and treat the toy ciphertext wrapper as the first glimpse of what it means to program with encrypted objects rather than ordinary arrays.

12.24 Where HEIR Fits Relative to JAX

Yes, we can bring HEIR into the examples, but we should do it honestly. The current official HEIR quickstart documents a Python frontend using a @compile() decorator, and HEIR also documents a Jaxite exit dialect for generating Python code against the Jaxite library API. That is slightly different from saying "HEIR takes arbitrary jax.numpy programs directly as input."

Current official picture. HEIR says "write a program in Python, annotate the types to mark which are secret, and HEIR will compile the rest," and the GitHub quickstart shows exactly that flow with from heir import compile. Separately, HEIR documents a jaxite dialect as an exit dialect for generating code against the Jaxite API.
So the right mental model is: JAX shows us the clean numerical target; HEIR shows us how an FHE compiler can take a high-level program and lower it toward encrypted execution; and Jaxite is one backend-facing path for Boolean FHE code generation in the HEIR ecosystem.

12.25 Side-by-Side Example F: Plain Python to HEIR Scalar Program

Idea:

Start with a small arithmetic function, but mark the inputs as secret so the compiler knows it must preserve privacy during evaluation.

Math:

\[ f(x,y) = (x+y)(x-y) + xy. \]

In HEIR:

from heir import compile
from heir.mlir import I64, Secret

@compile()
def func(x: Secret[I64], y: Secret[I64]):
    s = x + y
    d = x - y
    m = x * y
    return s * d + m
Why this matters. This is not just toy syntax. It is the official shape of the HEIR Python quickstart. The program is written at a high level, but secrecy is made part of the type information.

12.26 Side-by-Side Example G: HEIR Execution Flow

Idea:

A compiled HEIR function gives you an interface that looks much more like real encrypted programming: setup, encrypt inputs, evaluate on ciphertexts, then decrypt.

Math:

\[ c_x = \mathsf{Enc}(x),\qquad c_y = \mathsf{Enc}(y),\qquad c_z = \mathsf{Eval}(f, c_x, c_y),\qquad z = \mathsf{Dec}(c_z). \]

In HEIR:

func.setup()
enc_x = func.encrypt_x(7)
enc_y = func.encrypt_y(8)
result_enc = func.eval(enc_x, enc_y)
result = func.decrypt_result(result_enc)
This is exactly the sort of ciphertext exposure you asked for, but now using the real interface style shown in HEIR's official quickstart instead of only the toy wrapper we wrote ourselves.

12.27 Side-by-Side Example H: JAX View vs HEIR View

Idea:

The JAX version shows the numerical computation you want. The HEIR version shows the encrypted-computation interface you need.

Math:

Same mathematical function: \[ f(x,y) = (x+y)(x-y)+xy. \]

In JAX and HEIR:

# JAX / plain numeric view
def f_plain(x, y):
    return (x + y) * (x - y) + x * y

# HEIR / secret typed view
@compile()
def f_secret(x: Secret[I64], y: Secret[I64]):
    return (x + y) * (x - y) + x * y
Compiler lesson. The equation does not change. What changes is the programming model around it: secrecy becomes explicit, compilation targets encrypted operations, and the runtime manipulates ciphertext objects rather than plain arrays.

12.28 Side-by-Side Example I: Dot Product and the MLIR-Level HEIR View

The HEIR getting-started docs also show a dot-product example at the MLIR level. This is useful because it lets you see how a familiar linear-algebra computation is represented inside the compiler.

Idea:

Compute a dot product of two secret vectors by multiplying coordinatewise and summing the results.

Math:

\[ \langle x, y \rangle = \sum_{i=0}^{7} x_i y_i. \]

In HEIR MLIR:

func.func @dot_product(
    %arg0: tensor<8x i16> {secret.secret},
    %arg1: tensor<8x i16> {secret.secret}) -> i16 {
  %c0_si16 = arith.constant 0 : i16
  %0 = affine.for %i = 0 to 8
      iter_args(%acc = %c0_si16) -> (i16) {
    %x = tensor.extract %arg0[%i] : tensor<8x i16>
    %y = tensor.extract %arg1[%i] : tensor<8x i16>
    %m = arith.muli %x, %y : i16
    %s = arith.addi %acc, %m : i16
    affine.yield %s : i16
  }
  return %0 : i16
}
This is a great bridge example because the math is elementary, but the MLIR already makes the compiler structure visible: loop, extract, multiply, accumulate, return.

12.29 Ciphertext Exposure from the HEIR Lowering

The same official HEIR dot-product walkthrough shows what the lowered encrypted operations can look like after compilation to an OpenFHE-oriented exit dialect. That is exactly the kind of ciphertext exposure you want to get used to reading. 

%0 = openfhe.mul_no_relin %arg0, %arg1, %arg2
%1 = openfhe.relin %arg0, %0
%2 = openfhe.rot %arg0, %1 {static_shift = 4 : index}
%3 = openfhe.add %arg0, %1, %2
%4 = openfhe.rot %arg0, %3 {static_shift = 2 : index}
%5 = openfhe.add %arg0, %3, %4
%6 = openfhe.rot %arg0, %5 {static_shift = 1 : index}
%7 = openfhe.add %arg0, %5, %6

Idea:

Multiply encrypted packed data, then rotate and add to accumulate the dot product.

Math:

This is the packed analogue of \[ \sum_i x_i y_i, \] where rotations help align partial sums.

In Ciphertext Ops:

Now you can literally see operations like multiply without relinearization, relinearize, rotate, and add. This is what "ciphertext programming" begins to look like in a real compiler pipeline.

Part XIII: How to Read the Referenced Papers and Videos

13.1 Homomorphic Encryption Intro Material

When an intro video or document says "homomorphic encryption," make sure you extract these points:

  • What operations are supported?
  • What kind of data is represented?
  • What limits the computation?
  • Where does the overhead come from?
  • Why is the scheme still useful despite the overhead?

13.2 HEIR Material

When reading or watching HEIR material, focus less on syntax and more on architecture:

  • What input language is assumed?
  • What IR layers exist?
  • Where are layout decisions made?
  • How is the final backend selected?
  • What kinds of optimization passes are scheme-independent versus scheme-specific?

13.3 Matrix-Arithmetic Papers

When you read the matrix papers, ask the following every time:

  • What encrypted object is being represented?
  • What operations are native?
  • How many ciphertext multiplications are required?
  • How many rotations or key-switches are required?
  • What expensive operations are avoided?
  • Is the gain asymptotic, practical, or both?
  • Is the method better for large matrices, small matrices, or specific shapes?

Part XIV: A Practical Study Roadmap

14.1 Stage 1: Learn the Language

First goal: become fluent in the words. You should be able to explain plaintext, ciphertext, public key, secret key, homomorphic evaluation, noise, depth, bootstrapping, packing, rotation, relinearization, and CKKS out loud without notes.

14.2 Stage 2: Learn the Structural Bottlenecks

Before reading advanced papers, make sure you can answer these:

  • Why does noise grow?
  • Why are multiplications harder than additions?
  • Why do layouts and rotations matter?
  • Why is matrix multiplication such an important benchmark?
  • Why are compilers needed in FHE?

14.3 Stage 3: Learn the Scheme Families

Build a rough map:

  • BFV/BGV: exact arithmetic.
  • CKKS: approximate numeric computing.
  • TFHE family: Boolean / small-integer / LUT-heavy workflows.
  • Matrix-native proposals: redesign around linear algebra itself.

14.4 Stage 4: Learn the Systems Stack

At that point, you are ready to understand the whole chain:

  • High-level model or program.
  • Compiler / IR / layout optimization.
  • Scheme-specific encrypted kernels.
  • Hardware backend.
  • Performance and memory tradeoffs.
Final takeaway. FHE is not just one cryptographic trick. It is a stack. The stack includes cryptographic security assumptions, algebraic representations, noise management, packing strategies, compiler transformations, matrix kernels, and hardware-aware execution. The recent work around encrypted matrix arithmetic and HEIR is exciting precisely because it improves multiple layers of that stack at once.
